# RepoTunnel Remote Computers — native cross-platform development

Status: Remote MCP delegation, secure desktop enrollment, guarded text-source handoff, **cursor-driven approved-project source synchronization with binary staging**, portable source fingerprints, durable native test dispatch, SHA-256 verified resumable binary-artifact downloads, and isolated protocol tests are implemented. **Native Windows/macOS GUI acceptance, continuous/automatic mirroring of dirty worktrees, hardware-aware scheduling and embedded RustDesk screen viewing remain unimplemented/unverified.** Computers has an optional user-initiated external RustDesk launcher. This is an explicit acceptance blueprint, not a release claim.

## Intended experience

Develop a desktop app on Linux. Ask AI to validate Windows and macOS behavior through authorized remote RepoTunnel machines. The same remote computers can provide browsers, native AI Workspace, installed creative tools, spare GPUs, hardware/peripheral testing, parallel builds, data/video rendering, access to otherwise unavailable platform SDKs, and continuation on another machine.

## Actual implementation in this change

- Human desktop issues one 256-bit random credential with 24-hour expiry **only after selecting one approved project and explicit tool categories** (files, browser, desktop/AI Workspace, processes, source/artifacts, media). Remote machine persists only its SHA-256 hash and the selected project/permissions in bounded, private, crash-recoverable storage; max 12 grants. The local Computers page can list active grants (project, scope, expiry and **only a short digest prefix**) and revoke a **single selected credential** using its full digest internally, or revoke all grants. Revocation prevents subsequent receiver-side authorization even for an already authenticated machine MCP session; already accepted processes may continue. **Rollback protection:** credential authorization reads ONLY the valid current primary store, never a crash-recovery `.previous` copy, because restoring an older grant list could resurrect a revoked/rotated secret. If the primary is missing or damaged while an older backup exists, remote access fails closed until the human resets/reissues grants locally. Existing 24-hour credentials are not recoverable in plaintext. **Rotate credential** is a human-only, atomic selected-grant replacement: it keeps exactly the selected project and tool categories, generates a new 256-bit secret and 24-hour expiry, saves only its SHA-256 fingerprint, and invalidates the OLD bearer and its current MCP session on subsequent requests. The human must copy the NEW one-time secret to the coordinating desktop and reconnect; existing remote processes may continue. The coordinator Computers page offers **Re-pair with new credential** on an already enrolled node: it reuses the same validated HTTPS endpoint and exact previously approved project, performs fresh authenticated MCP handshake plus project binding, and replaces the old in-memory connection only after verification succeeds. A failed re-pair leaves the prior node intact; an AI-owned node refuses re-pair until the human explicitly disconnects it, preventing silent ownership changes. Each old connection has a short-lived re-pair gate; a successful swap or explicit disconnect permanently blocks stale references to its previous transport so they cannot initiate another remote action. AI ownership is rechecked **inside** that gate before being claimed, preventing a rejected concurrent request from leaving a spurious owner lock. No remote commands are retried or replayed; already-dispatched requests may have uncertain outcomes requiring inspection. If the rotation reply is lost, the new secret cannot be recovered, so reissue a fresh grant locally instead of blindly retrying the old fingerprint. Legacy machine grants with no recorded scope are refused during tool calls and must be reissued.
- Coordinator desktop Computers screen connects up to eight remote HTTPS MCP endpoints and binds each node to exactly one remote workspace ID explicitly copied from the issuing machine. Every forwarded project-scoped tool call must target this exact ID; the receiver independently checks the credential's approved workspace. Tokens remain in memory, never returned to AI or written into projects. URL must use HTTPS, without embedded usernames/passwords, query strings or fragments. TLS is verified by the normal Rust client.
- **Optional remembered computers (restart-safe, never auto-connected):** an authenticated connected node has **Remember pairing details** in Computers. Explicit opt-in saves only its bounded machine name, canonical HTTPS MCP endpoint and exact paired project ID in a private app-data JSON preference; no bearer, handshake session, tool grants, AI owner, browser information or process state is serialized. After app restart, **Fill connection form** restores those non-secret fields only; the human must enter a fresh valid credential and click Connect, which re-verifies the authenticated project binding. **Forget saved details** removes the stored profile, without disconnecting live sessions; prior metadata backup copies are also removed and never automatically restored. A failed connect clears the credential field. Host metadata is personal information, so saving is off by default.
- Official Rust MCP SDK performs handshake, tools/list, SSE and tool calls; no new remote shell or screen protocol.
- Optional View screen in RustDesk field: a human enters a peer ID and clicks a button in the Computers page. RepoTunnel uses a bounded direct --connect argument with the locally installed RustDesk binary, no shell, no AI authority, no password handling, and no automatic installation. RustDesk maintains its own remote-screen consent and authentication.
- Local AI sees list_remote_machines, remote_machine_call, sync_remote_source_files, advance_remote_project_sync, the native-test matrix controls and artifact transfer tools; it cannot issue credentials, enroll nodes or revoke permissions. Exactly one AI owner claims a connected remote node until the human disconnects and reconnects.
- The remote computer receives normal MCP calls and still enforces its own project approval, AI Pause, command sandbox, browser tab ownership, local change review, Google page restrictions, Team/Mission and native desktop permissions.
- **Both coordinator and receiver** restrict machine credentials to a bounded tool allowlist: the remote HTTP gateway parses bounded JSON-RPC requests for a verified machine credential and rejects unlisted `tools/call`, recursive remote delegation, local-only approvals, credential management, Git publishing and unrelated MCP methods. Existing remote workspace, AI Pause, browser and native-app permissions still apply. **Receiver-enforced scoping:** every machine-authenticated JSON-RPC tool call is checked on the RECEIVING computer against that token's specific approved project and selected capability categories, with unclassified or privileged integration actions blocked. Unknown RPC methods and JSON-RPC batches are refused. The remote gateway also limits request body size and revalidates the grant on each POST. Machine-authenticated `list_workspaces` tool calls are now denied to prevent enumeration of unrelated project names/IDs; the issuing desktop displays the single approved ID alongside the credential, and the coordinator stores only that explicitly entered ID. MCP `tools/list` still discloses tool names, not workspace data. Do not expose machine credentials to untrusted computers. Machine-authenticated MCP sessions now bind the server-issued `mcp-session-id` to a SHA-256 fingerprint of the issuing credential in a bounded in-memory registry; the gateway checks that ownership on subsequent POST, GET/SSE, and DELETE, and rejects an OAuth or private-tunnel caller trying to reuse a machine-bound session. Each request also rechecks the original credential's live approved project and nonempty capability grant. Unknown/missing/malformed session IDs are refused for non-initial machine requests, and `initialize` must receive a valid server session ID. These paths have unit and real local Rust MCP client/server tests; an independent security review of proxy/TLS identity, revocation under races, and physical multi-node behavior is still outstanding.
- **Cryptographically signed installation identity and trust-on-first-use (TOFU) pinning:** each receiving RepoTunnel generates its own persistent Ed25519 signing key on first use, keeps the PKCS#8 private key inside app data (owner-only 0600 on Unix), and exposes only a SHA-256 fingerprint of the public key to its local Computers screen. The remote **verify_machine_project_binding** tool requires a fresh 256-bit caller nonce, signs a domain-separated message containing the exact credential-approved workspace ID and nonce, and returns the signature with the public key. The coordinator checks that signature, exact project ID and fresh nonce before enrollment, on project-bound health/inspection, **and immediately before every AI-delegated tool dispatch (including global capability inventory calls)**. A newly detected identity swap blocks the operation before remote side effects; this cannot substitute for TLS/SPKI channel pinning against a malicious transport that switches endpoints between separate HTTP requests. The Computers screen displays both installation fingerprints for an independent first-time comparison. **Remember pairing details** persists the public-key fingerprint beside the HTTPS endpoint and approved project, then later connect/re-pair refuses a changed signing key even when a bearer is otherwise valid. Re-remembering an already pinned node may rename it but cannot replace its pinned key/project; the human must explicitly forget and freshly enroll a changed installation. The private key survives app restart, and malformed key files, symlinks, hardlinks or permissive Unix file modes fail closed without silently rotating the identity. Newly created Unix identity directories use owner-only permissions (0700); an existing directory writable by another user or not owned by the current user, a symlinked directory, or a Windows reparse-point directory is refused rather than silently repaired. On Unix the key is opened using `O_NOFOLLOW`/`O_NONBLOCK`, and its opened inode, link count, file type, size and permissions are independently checked to reject file replacement between inspection and open. If an existing app-data directory is rejected, an operator must verify and repair its ownership/permissions locally before pairing; RepoTunnel does not auto-rotate its identity. Prior saved profiles without a fingerprint remain visible for manual removal, but cannot be trusted or connected until deliberately forgotten and re-enrolled. Invalid, legacy unsigned, replayed, foreign-project or malformed challenge receipts fail closed. This is software installation key continuity (TOFU on verified HTTPS), **not** hardware identity attestation or TLS certificate/SPKI pinning. Protect the remote installation key: a different app install or regenerated key necessarily requires manual re-enrollment.
- The Computers page also offers **Inspect remote jobs**, a separate, human-triggered **read-only** call to `get_workspace_runtime_status` for the exact paired project. The coordinator checks every returned process belongs to that project and shows at most 24 process IDs, bounded labels, states and exit codes, never the shell command or stdout/stderr. Credentials lacking the process category are refused. The snapshot can be incomplete and does not stop, replay or cancel jobs.
- The Computers page additionally offers **Inspect browser runtime**, a human-triggered authenticated read-only `get_browser_status` probe on the paired project with the **browser** capability grant. It reports only detected browser availability, whether a browser is running *in the diagnostic MCP session*, and an optional bounded browser name. It does NOT open a browser, inspect other AI sessions/tabs, expose executable paths/CDP ports/session IDs, take ownership, or certify browser automation readiness. A running browser in another isolated AI session may not appear in this probe.
- The Computers page also offers **Inspect native capacity**, a separate explicit, read-only authenticated call to `get_system_resources` on that node's exact paired project. It requires the **process** capability grant and reports OS, architecture, available RAM/disk and detected GPU count only when the receiving machine confirms them. Missing/denied/malformed responses fail closed. This does not acquire AI ownership, execute commands, start browsers, validate installed SDKs or certify native GUI readiness.
- **Optional health monitor:** the Computers page offers an off-by-default toggle to re-check the existing authenticated MCP connection for enrolled nodes every 60 seconds while the page is open. Checks are read-only, timeout-bounded, skip overlapping cycles, show per-machine errors/capability changes, and stop when the toggle is off or the page closes. It never stores credentials persistently, silently rotates/reconnects the bearer, acquires remote AI ownership, or replays a remote mutation. A failed check needs human-led re-pair.
- The Computers page has a manual **Check connection** action that revalidates the approved project via the same authenticated challenge, then checks bounded MCP `tools/list` metadata on the existing session, without acquiring AI ownership or launching software. It reports reachable protocol metadata and whether advertised tools changed; this is **not** browser readiness, native display readiness, credential renewal or automatic reconnection.
- Existing remote browser actions, screenshots, native AI Workspace sessions/screenshots/actions, native application control, file actions inside approved workspaces, builds/processes and media tools are accessible where supported by the remote installation. **AI Workspace capability reporting follows its actual native backend:** available by default on Linux; Windows/macOS native AI Workspace requires the explicit remote-machine experimental opt-in `REPOTUNNEL_EXPERIMENTAL_NATIVE_AI_WORKSPACE=1`, is not silently enabled by a remote credential, and is not yet physical-hardware acceptance tested. The MCP `capabilities.desktop.aiWorkspace` flag now reflects the effective platform setting rather than reporting every non-Linux build as unsupported.
- Source handoff through sync_remote_source_files: preview selected approved local text files, compare SHA-256 on remote, create missing files in existing remote folders, or patch differing files only with a previously previewed expected remote SHA. Remote review and permissions apply; successful edits are read back and hashed.
- **Computers desktop source-diff preview:** select any already approved *local* project under the paired remote node and click **Preview source differences**, then **Next 8 files** for further SHA/size comparisons. After the last page, **Recheck whole-source parity** runs a fresh local inventory and single remote aggregate SHA/count/byte inspection with the original source fingerprint, without requesting another per-file page, transferring data, or assuming that the previously reported file breakdown is still current. A changed local inventory clears the stale UI result and requires restarting the preview. The coordinator resolves the remote project exclusively from the human-paired node, uses read-only source-scoped authenticated MCP methods directly (without claiming AI ownership), and displays identical/missing/conflict/unverified states. It never transfers, overwrites, stages, runs, or deletes files. The last page only reports full source parity after a matching aggregate snapshot; conflict resolution and actual source imports still require their own explicitly approved guarded flow.
- **Bounded multi-page source inspection:** the Computers source-diff section also offers **Scan next 64 files (read-only)**, which performs at most eight sequential requests of eight files each and verifies the paired node/project, exact source fingerprint, total inventory, cursor, row count and forward progress after every response. **Stop after current page** prevents subsequent pages without cancelling an already outstanding read; accepted rows and cursor remain available for an explicit resume. A stale fingerprint or malformed later response clears the entire accumulated preview rather than allowing a mixed-version conflict report. The scan never stages, imports, overwrites, runs or silently resolves remote files; this action does not claim AI ownership or replace any required remote approval.
- **Exact-path status and positive-missing proofs:** remote source-status replies now must echo the exact requested canonical source path for both AI coordination and human read-only preview/preflight. A mismatching remote `relativePath` is rejected instead of being treated as evidence for another file. Source create-only planning proceeds only when the receiver explicitly reports `status: missing` with absent or null hash/size; malformed `missing` receipts with bytes or SHA metadata fail closed. A real MCP regression simulates a receiver returning metadata for a different path.
- **Strict read-only source-review evidence validation:** every Computers source page now validates the 64-character lowercase source fingerprint, SHA-256 hash lengths, safe numeric sizes and cursors, canonical relative paths, status/metadata consistency, and the absence of duplicate or case-/Unicode-normalization-aliased paths across all pages (including identical files). Failed or stale pages invalidate collected issues and draft decisions rather than displaying mixed or forged evidence. The native source-audit endpoint also treats contradictory or malformed remote metadata as **unverified**, never as a trustworthy missing/conflict/identical result, and re-hashes the approved local source **after each page**, including partial previews and mismatching aggregate reports. This protects manual review evidence but does not itself authorize any remote mutation.
- **Race-safe human source review lifetime:** a refresh that observes a different paired installation, random connection generation, or approved remote project now clears existing comparison pages, per-file choices, outstanding read-only preflight receipts, and parity watcher evidence. Any source audit, create-only preflight, or aggregate recheck already in flight must revalidate the *current* paired node and selected local project before publishing its result. Requests finishing after Computers closes cannot repopulate the UI. Concurrent refresh requests have monotonically increasing generations, so late stale refresh replies cannot restore an earlier connection. Focused tests force re-pairing while a page or preflight reply is delayed and reverse the order of two refresh replies; no stale source evidence or write action survives.
- **Guided human create-only proposal preflight (read-only):** Computers now offers **Preflight next 8 proposed files (read-only)** after a completed bounded source inventory; it accepts only files explicitly marked `proposeCreate`. The dedicated `preflight_remote_create_only_desktop` Tauri command checks the current complete local source manifest against each supplied exact path/SHA-256/size and the original inventory fingerprint, then performs at most eight independent `get_remote_source_file_status` inspections under the already authenticated, project-bound connection. Only positively missing paths can pass; null hash/size metadata is normal for missing files, but any non-null metadata, reported path substitution, existing source, changed local snapshot or pairing generation is refused. Each successful batch returns only the selected path/hash/size evidence and is **not** an authorization to stage, mutate or overwrite. The UI invalidates old preflight receipts when selection, inventory or machine pairing changes, and any subsequent mutation remains a separate explicitly approved action with create-new-only semantics.
- **Durable human source-review intent (NOT remote authorization):** Computers now offers **Record reviewed create-only intent (no transfer)** for the first at-most-eight freshly preflighted missing files. Before recording, the human sees and explicitly confirms the exact file paths, full SHA-256 hashes, byte counts, source inventory SHA-256, local and destination approved project IDs, pinned machine signing-key fingerprint, and random connection generation. The Tauri command independently recomputes the complete current source inventory and performs new read-only receiver positive-missing checks before persisting an immutable `awaitingReceiverApproval` receipt in private app-data (`remote-source-human-intents.json`). The journal is bounded by record count and bytes, protected by a local OS writer lock, and refuses rollback to an older `.previous` backup. An identical request returns its existing receipt instead of generating duplicate evidence. An operator can explicitly **Withdraw saved source proposal**: the coordinator durably transitions that exact receipt to `withdrawn`, refuses recreating the same selection under the old connection generation, and preserves non-reusable historical evidence. A lost withdrawal acknowledgement is reconciled using only the local read-only journal, never by automatically resending; damaged current state cannot roll back to an older unwithdrawn snapshot. On a lost desktop create acknowledgement, the UI likewise reads the journal rather than automatically resending the write; receipts remain visible after refresh and are marked historical if the pairing changed. **This is reviewed proposal evidence only**: no bytes are sent, no receiver authority is claimed, no AI session is impersonated, and this receipt alone cannot authorize a remote write. A separate receiving-machine approval and a second explicit human Import confirmation are required. Saved pending receipts additionally expose **Recheck saved proposal status (read-only)** on the original still-connected pairing only. The backend reloads the immutable proposal, independently checks the exact approved local source inventory, inspects at most eight remote paths by authenticated, connection-pinned read-only MCP, and re-hashes the local project afterward. Results explicitly distinguish missing, identical-byte, conflicting, and unverified remote states; even identical bytes **do not prove** that RepoTunnel installed them or that any receiver approved an import. Withdrawn or re-paired receipts cannot be reconciled as current, and the UI validates every returned pairing, file size and digest. The receiver-side independent approval, verified staging and one-shot create-only import are now wired through the Computers workflow; they require separate explicit human confirmations. Different app-data stores are not a shared authority.
- **Receiver-local human source-approval review (no transfer yet):** On the sending computer, a saved pending source-review intent is freshly re-preflighted against the original connected pairing and signed using its protected Ed25519 installation identity, then exported as a bounded `RepoTunnelIncomingSourceReviewV1` JSON containing the exact original coordinator and intended receiver installation fingerprints, source/destination approved project IDs, original random connection nonce, source fingerprint, review ID, and up to eight selected paths/sizes/SHA-256s, with no bearer credentials or source bytes. On the RECEIVING computer's own Computers screen, a human pastes the draft, independently compares the receiving installation identity and sender identity, selects an existing unexpired credential with source scope for that exact receiver project, and explicitly confirms each file. The native receiver independently checks credential metadata, its own approved read-write workspace, the exact positive-missing status of all destination paths (including rejection of existing symlink/reparse-point ancestors even when they lead elsewhere INSIDE the approved project), their portability and absence of duplicates, then stores a receiver-generated durable `approved` evidence receipt in bounded private app data (`remote-source-receiver-approvals.json`), with a cross-process OS writer lock and fail-closed refusal to roll back a corrupted primary. Idempotent repeated exact reviews return the same record; changed hashes/projects/credential for one review ID and withdrawn records are refused. Human withdrawal is permanently recorded without importing a file; the UI recovers lost acknowledgements with read-only listing instead of retrying a write. The receiver independently verifies the domain-separated Ed25519 signature over the exact immutable source-review manifest and rejects changed sender/receiver identities, project IDs, nonce, source fingerprint, path, size or hash; the public key's SHA-256 must equal the declared coordinator fingerprint, and the draft must target the receiver's actual installation fingerprint. Legacy unsigned saved receiver receipts remain readable only as `legacyUnsigned` historical evidence and cannot authorize imports or be reapproved under the old review ID. **This establishes signed review provenance but not a live authenticated sender session or bearer binding**: a future import handler MUST independently verify the actual authorized paired credential, originating installation identity, session, nonce, approved exact paths/hashes, latest receiver approval state and receiver policy again. These local approval records are **not remotely usable capabilities**, and no new remote stage/import MCP method is enabled. Human-approved remote create-only import, durable before-send unknown-outcome journal, and transfer ownership/restart recovery remain unfinished.
- **Independent receiving-machine source approval (separate from import):** Computers now lets the coordinator copy an exact pending `RepoTunnelIncomingSourceReviewV1` proposal JSON for explicit, out-of-band review on the *receiving* RepoTunnel desktop. The receiving human must select its own unexpired **source-scoped credential** for the exact receiving approved project, review the original coordinator installation fingerprint/project/connection generation, source aggregate SHA-256 and every at-most-eight file path, size and SHA-256, then explicitly confirm. The Tauri-only `approve_incoming_source_review_desktop` command independently checks the live receiver-issued credential, its `source` category and approved workspace, read-write workspace policy, canonical/safe and positively missing destination files before saving a separate bounded `remote-source-receiver-approvals.json` journal. It has an OS writer lock and refuses rollback to stale backups or duplicate/substituted review identities. The receiver can **withdraw** an approval permanently and recheck it locally read-only: a rotated/revoked credential, removed read-write permission or occupied destination invalidates proposed create-only eligibility without modifying remote files. Lost local save/withdraw acknowledgements are reconciled by reading the authoritative receipt rather than blindly replaying changes. **Machine-authenticated receiver approval inspection:** The read-only MCP tool `inspect_machine_source_review` accepts only the exact receiver workspace ID and independently generated receiver approval ID. The HTTP gateway derives the caller's machine credential SHA-256 from its live bearer-bound MCP session, revalidates the incoming RPC grant scope (`source`) and exact workspace, and blocks OAuth/other credentials from borrowing that session. The receiver additionally compares that verified credential fingerprint and workspace to the durable human approval before returning only the current approval state and bounded per-file destination statuses. Caller-supplied credential fingerprints are never accepted. This endpoint cannot issue/withdraw/replay approval or modify files, and matching destination hashes still do not prove import success. The coordinator Computers screen can accept the receiver's independent approval ID out of band and inspect it only through the ORIGINAL connected machine generation and existing machine credential; the desktop validates the full signed review source-project, receiver-project, both installation signing fingerprints, nonce, aggregate SHA-256 and every file path/hash/byte count again, discarding stale React results after a re-pair, changed receipt ID or source-review revision. No import action is exposed by this lookup. **Approval receipts are not RPC capabilities and do not install source files:** the receiver now also has a tested, local-only, one-way `dispatchUnknown` journal transition in the same OS-locked approval store. This reserves the exact review against one live-identity/session/staging context BEFORE an eventual import attempt, refusing repeat reservations after lost ACKs, restart, withdrawal, credential revocation, destination races or changed identities; damaged primary receipts never recover stale approval backups. Read-only receipt inspection reports `missing`, `matchingBytes`, `conflict` and `unverified`, but identical bytes cannot prove import provenance. The authenticated machine-only execution RPC now verifies its live gateway-derived principal, exact approved manifest and completed session-owned staging before consuming this reservation and installing create-only; the coordinator desktop additionally saves a durable dispatchUnknown marker before the final RPC. The reservation helper by itself does not transfer or install files. The receiver checks the coordinator Ed25519 signature against the full proposed immutable manifest and claimed signing-key fingerprint, plus its own receiver identity, while still requiring human out-of-band comparison of known/trusted installation keys. This is signed offline review provenance only, not proof of a live authenticated peer or permission to execute a remote write.
- **Remote receiver approval inspection over the actual paired credential (read-only, not import):** The receiver now advertises `inspect_machine_source_review`, available only to a still-approved, source-scoped machine credential in the gateway's credential/project allowlist. Unlike a user-provided `credential_fingerprint`, the receiver derives its caller's SHA-256 from the gateway's **live, bearer-bound MCP session registry**, then checks the exact persisted receiver approval ID, project and selected machine grant. Public OAuth/AI requests cannot borrow an existing machine-owned session. The receiver returns a bounded status plus a binding to the previously signed human review, never the credential or file bytes. On the sender's Computers panel, the operator can enter the receiver's independently generated `receiver-source-…` receipt ID for the original saved review and click **Inspect receiver human approval on paired machine (read-only)**. The coordinator re-verifies the original remote signing key and random connection generation, permits only the read-only tool, checks that source-review ID, local/coordinator fingerprint, projects, inventory SHA and every file path/size/SHA are unchanged, and refuses stale replies after disconnection/re-pair or a human edit-and-restore of the receiver receipt field. `approved`, `missing`, `matchingBytes`, `conflict`, `withdrawn` and `dispatchUnknown` are **observations only**; a reported approval does not provide live write consent and cannot be spent to import. The machine-authenticated one-shot human-import executor now records imported only after post-install SHA-256 verification and durable receiver completion; lost acknowledgements remain dispatchUnknown and are never replayed.
- **Human import staging admission (internal, not remotely executable):** New receiver checks match 1–8 selected reviewed paths to unique generated 128-bit staged file IDs, enforce completed session-owned source checkpoints, verify the exact SHA-256 and length of each binary payload, and reject partial transfers, different machine/session owners, duplicate IDs, changed signed hashes, missing tasks and destination races. The source-transfer cross-process OS lock spans verification and durable one-shot `dispatchUnknown` reservation. A separate gateway helper derives a distinct `human-source-v1` staging owner from the **verified machine credential fingerprint, actual MCP session and exact receiver approval ID**, not caller-supplied identity or an AI session. An internal constructor binds that principal to the original signed human receiver approval and can never authorize withdrawn/used consent. Machine-only approved staging and import tools now connect the sender's Computers Import button to actual receiver create-only installation. Unix imports use no-follow anchored directory handles and atomic linkat. Windows human imports now use the native NT `RootDirectory`-relative per-component no-reparse opens and a flushed sibling stage linked into the final destination using `FileLinkInformation` with replacement disabled. The older path-based fallback is never used by the human workflow. Windows-native compile/runtime and adversarial reparse-point tests still require a real Windows environment. Receiver read-only inspection explicitly returns `humanImportSupported=false` and `canStillProposeCreateOnly=false` on Windows, which hides the coordinator's Import button and shows a human-visible explanation. The native sender also rejects that preflight before reserving its own one-shot transfer task, including when a stale UI attempts direct dispatch.
- **Executable human-approved source import (Computers):** After the originating human signs an exact source-review intent and the receiver independently approves that review, the coordinator re-inspects the receiver receipt on its original pinned MCP connection and requires a separate explicit **Import the approved source files (create only)** confirmation. The coordinator durably records a generated staging-task ID before sending bytes, authenticates only through the paired machine session, and stages exact approved binary files (including empty files) in bounded 256 KiB SHA-256-checked chunks. The receiver enforces original project, credential, session, signed path/size/hash, and task-derived file ID on *each* stage request. Before install the coordinator re-hashes the originating project, writes its own durable `dispatchUnknown` barrier, and invokes the receiver's dedicated machine-only import endpoint; the receiver verifies every completed session-owned stage, checks missing destinations, durably consumes the independent approval, installs atomically create-only and independently verifies destination hashes. Unix installs use no-follow directory descriptors and `linkat`; Windows human-source import now has its own handle-anchored native create-only installer instead of the unsafe path-based fallback; Windows acceptance tests and platform-specific compilation remain for the user's real-device verification. Lost staging-task or chunk acknowledgements are reconciled through machine-session-scoped **read-only** task/checkpoint inspection; exact committed SHA-256 and byte offsets are required before continuing, and failed inspections halt before installation. This also supports authenticated empty-file checkpoints. Lost **final installation** acknowledgements are **never** automatically replayed; a receiver-side successful import can be independently inspected by the original approval ID plus original one-shot staging task ID. Desktop pairing discovers the five machine-only methods (three stage/install operations and two read-only staging inspections) without adding them to generic AI-delegable remote calls. Even an `imported` execution response does not complete the sender journal until a separate machine-authenticated read-only receiver inspection verifies the same durable task ID, imported state, and every installed file's exact approved SHA-256 and size. If inspection fails or the files have changed, the sender remains `dispatchUnknown` and never replays the installation. For a genuinely lost final import ACK, Computers now exposes a separate explicit **Record verified import in local journal** action only after the UI has read-only proof of the original receiver imported receipt and matching hashes. Its dedicated native command independently re-reads the same signed approval, original staging task, and every destination digest, then conditionally moves only the *local* saved sender journal from `dispatchUnknown` to `imported`; it never sends any transfer/install mutation. Failed proof retains UNKNOWN. React shows staging progress, imported/unknown/pre-install-failure results, and restart-recoverable attempt receipts. Validation on one Linux test host does **not** establish verified operation between two physical computers or Windows race safety.
- **Human source conflict review draft:** for the read-only Computers preview, an operator can now mark each inspected missing source as deferred or proposed for a later create-only transfer, and each existing-file conflict as requiring manual merge or keeping the remote version unchanged. `Copy source conflict review draft` exports every inspected issue (not just the currently visible 40), exact node/project IDs, verified machine signing fingerprint and random connection generation, local source fingerprint, sizes and SHA-256s, and a partial/full-scan flag to the local clipboard without exposing source bytes or credentials. - **Complete human conflict review:** Computers now keeps all inspected missing/conflicting/unverified rows from the current read-only source comparison (bounded by the native 6,000-file manifest budget) and paginates the detailed display at 40 issues per page. This replaces the earlier first-40-only issue sample: an operator can revisit later conflicts without silently discarding their paths or SHA/size evidence. Continuing a stale or failed comparison clears its old preview rather than displaying unverified rows as current. No overwrite/import action is exposed by these review controls, and closing Computers still discards this in-memory comparison.
- **Source-sync cursor generation binding:** the multi-chunk AI `advance_remote_project_sync` workflow returns the active random `connectionNonce` in every progress receipt. ## Security and technology decisions

The remote RepoTunnel is the enforcement boundary. No unrestricted SSH shell, bypass of remote approvals or browser ownership, automatic credential export, silent software installation, firewall/VPN changes or background source uploads. Screen sharing is optional, not mandatory for structured MCP delegation. RustDesk OSS is a candidate for external viewing; its server uses separate rendezvous and relay processes. Review RustDesk AGPL obligations before embedding code. Tailscale, SSH and other network solutions are transport options, not substitutes for machine-local permission policy.

The local controller never receives access to remote credentials beyond the user's explicit UI entry, never exposes them through AI calls, and should not retry ambiguous actions blindly. Remote tool output is untrusted data. macOS UI automation may require local Accessibility/Screen Recording permission; Windows service contexts are not interchangeable with an interactive desktop session.

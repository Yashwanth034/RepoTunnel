# Cross-platform feature parity and native acceptance gates

Last source inspection: 2026-10-18. This is a working checklist, **not** a claim of native Windows or macOS acceptance.

## Non-negotiable completion rules

A feature is complete on an OS only when (1) its real native path is implemented, (2) the safety and permission model matches Linux, (3) native automated tests pass, (4) a realistic normal and failure-path scenario is exercised, and (5) crash/restart behavior is safe. A Linux test or a compiled installer is not sufficient. Never turn an unavailable sandbox/watch into unrestricted execution to make a test pass.

Do not build installer packages during ordinary development. The source-only `.github/workflows/cross-platform-source.yml` workflow provides native Windows and macOS typecheck/frontend build/strict Clippy, **links the actual native Tauri desktop executable (`cargo build --bin repotunnel`)**, and runs native Rust library tests on pull requests or manual dispatch. The executable link stage catches platform-specific FFI/library failures that Rust source/type checks alone can miss; it creates **no installer or published artifact**. The existing release workflow remains the signed-installer gate. These checks have not run on the current uncommitted workspace changes and are not a replacement for real desktop security acceptance.

## Milestones

1. **Sandbox parity:** native task command policies, source mutation view and Mission sparse isolation. Refuse to advertise parallel isolation until the boundary is proven on each OS.
2. **Reliable autonomous operation:** native Task Integrity event watching, project monitoring, managed process identity/reattachment and port visibility.
3. **Native AI Workspace:** separate architecture per OS rather than treating Linux X11 code as portable; integrate native capture only after security guarantees and cleanup are verified.
4. **OS user experience:** executable resolution, resource telemetry, browser/video/phone real-device acceptance, safe Direct HTTPS pathways.
5. **Release-grade validation:** macOS update restore-on-failure, Apple signing/notarization, Windows signing/install smoke, native accessibility permission tests.

## Update installation safety checkpoint

The existing signed-update discovery flow remains available on macOS; **macOS installation is deliberately blocked** until native failed-replacement/restore acceptance proves that the installed app remains intact. On supported platforms, installation now uses an exclusive in-process guard, checks active work both before and after fetching update metadata, inspects complete durable terminal and managed-process histories (not the dashboard's first 100 records), and blocks for running/replanning Agent Missions. Corrupt, missing or unreadable critical activity state fails closed rather than permitting installation. An existing empty or invalid update-state file is not treated as fresh defaults, and failed update requests do not replace settings with default records. After an update starts, failed persisted-state health validation retains pending-install evidence for a subsequent startup retry; only a healthy launch clears that evidence and records the new version as successful. An installer error does not promise successful rollback without inspection. Tests include a 150-entry active-history case; Linux source tests do **not** substitute for native Windows/macOS update acceptance. The updater now downloads and verifies the signed package separately, then rechecks active work immediately before calling the native installer; this closes the long download-window gap. Process-history reconciliation conservatively retains running records when durable supervisor state is missing, mismatched, or unreadable. A separate updater preflight scans the same bounded supervisor candidates as recovery, refusing installation if an orphan running/pending supervisor cannot be proven stopped or its spec/state metadata is missing or corrupt. A previous-good backup that still reports running work also blocks installation. Native process exit/identity behavior and the remaining race where new work starts after the final check still require acceptance; macOS installer/restore behavior is not release-accepted.

## Updater rollback evidence and managed descendant-stop safety (2026-10-18 continuation)

The updater now distinguishes failures before native installer invocation from failures after invocation. Before invocation, a failed download/preflight clears only its new pending record; after invocation, an installer error retains pending version evidence and blocks another install until restart reconciliation. An unexpected installed version or unreadable core persisted data also keeps the pending evidence. Returning to the old version clears that evidence only after core persisted data is readable; the intended new version must pass its existing post-update health check. Failed recovery-evidence persistence is surfaced as an error instead of silently ignored. macOS installation remains deliberately blocked pending genuine native restore-on-failure acceptance.

Managed-process stop and Stop All now require a final supervisor record matching the original process ID, supervisor PID, and kernel identity, with no child PID still attached. On Unix, the original process group must be verified absent so a terminated shell leader cannot hide surviving same-group descendants. On Windows, the supervisor process must be verified exited before reporting success because its kill-on-close Job Object remains open while the supervisor lives. The added Unix/process-record regression tests run on Linux; native Windows Job Object exit and real macOS group/descendant behavior still need platform acceptance. A Unix process that escaped its original process group is not proven contained by this group check alone.

## Windows managed Stop receipt and AppContainer helper launch containment (2026-10-18 consolidated milestone)

The Windows Stop/Stop All path previously depended on a terminal receipt written by a supervisor that `TerminateProcess` itself ended abruptly; even successful Job Object tree containment could therefore leave a durable `Running` state and fail to report a stop. Windows now records whether the OS termination of the **identity-verified original supervisor** was confirmed. If the durable supervisor state remained Running, it can write a recovery Stopped receipt **only** when its original supervisor/child PIDs and creation identities match the last snapshot, the original child identity is known, and the kernel reports both processes exited. Running, unknown, recycled, mismatched or unverified exit is still rejected. If the supervisor remains live or unreadable, Stop retains its in-memory handle instead of detaching it early. The exit checks occur before cleanup of the local runtime handle. Portable tests cover no-kill, alive/unknown process, PID/identity/state mismatch and valid terminal evidence; the existing Windows Job Object descendant-kill test must run on native Windows before claiming real Stop parity.

The AppContainer launch record, consumed by a helper running outside the restricted child token, now validates the generated profile identity, original runtime directory, unused exact-format cleanup manifest/staging path, and project-scoped working directory before creating a profile or changing ACLs. Cleanup also refuses unrecognized recovery receipt, profile or runtime paths. Critically, the launcher explicitly pins its **host temporary-directory root** separately from the helper's intentionally private TEMP/TMP variables, so the validation uses the correct original OS temp directory rather than accidentally rejecting all legitimate helper launches. Portable fixtures cover permitted paths, unrelated directory escape, wrong working directory/profile, planted receipt and pending file, and replaced symlink runtime. ## Windows native source-mutation project projection (2026-10-18 continuation)

Windows source-mutating task execution now has a source-level AppContainer backend rather than an unconditional unsupported-platform refusal. RepoTunnel copies a bounded subset of the approved project into a fresh disposable, project-shaped directory (maximum **4,096 files / 64 MiB**, with an **8,192-directory** bound). Git metadata, protected or sensitive-named paths, dependency folders and generated build trees are omitted; symlinks, junctions and other reparse points fail closed. Task-approved exact and prefix source paths are restaged from the already-authorized private task source view, not written in the original project. The command runs with its CWD under the disposable projection. Windows AppContainer receives recursive read access on the disposable projected root and write ACLs **only** for approved exact files and directory-prefix scopes; no AppContainer read, write, or temporary deny ACL entry is applied to the authoritative original project. A source-view scope that does not yet exist as a grantable target fails closed (new file creation must use an existing approved parent/prefix).

After a successful command, RepoTunnel scans the projected files and directories without following aliases, compares the snapshot against the pre-command baseline, rejects edits, additions, deletions and directory changes outside task source scopes, and copies **only** authorized file changes back to its private source view. The original project is still untouched; its changes can be applied only by the existing separately authorized Task Integrity / Change History reconciliation, which may block or roll back. Commands that fail or time out do not synchronize projected writes. The workspace projection is temporary and cleaned up. This is a deliberately bounded copy rather than a transparent full-project native mount: very large workspaces, special files, directory-only changes, and tools that require excluded build/dependency directories are not yet supported by this path.

Portable tests verified approved exact/prefix file edits and creation, base immutability, refusal of out-of-scope file and directory changes before any synchronization, original-source symlink rejection, and **two simultaneous private task copies editing the same filename independently**. A Windows-only AppContainer test has been added for an authorized private edit and an attempted absolute write to the real project but **has not run on Windows**. The native Windows ACL grant, command spawning, rollback/termination, absolute-path denial and process-tree behavior therefore require native acceptance before treating this as supported production isolation. The Mission scheduler still uses serialized execution on native platforms until end-to-end concurrent-writer acceptance and safe integration are proved; that guard was not bypassed.

## Windows copied-project ACL propagation and crash-cleanup parity (2026-10-19 continuation)

A Windows native acceptance review identified a real execution blocker in the new private-copy source path: the AppContainer received inheritable read rights only on the *root* of an already-populated copied project, and existing files/descendants did not necessarily receive those rights. Existing files inside authorized prefix scopes could likewise lack Modify permissions.
